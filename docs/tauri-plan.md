# Matsuko Editor：Rust + Tauri での実装計画

作成日：2026-11-26
対象：動画編集ソフト Matsuko Editor（デスクトップ版）
前提にしたもの：`src/matsuko-editor.html`（ブラウザ版。読み込み・カット編集・範囲書き出し・テロップ・無音検出まで動作）、HANDOFF の方針（beta で `.swdx` に移行、Cloudflare を使う共同作業基盤）

---

## 1. ねらい

ブラウザ版で確かめた画面と操作を、そのままデスクトップアプリに移す。ブラウザ版の限界は次の4点で、デスクトップ化でこれを解消する。

| ブラウザ版の限界 | デスクトップ版での解決 |
|---|---|
| 書き出しに実時間かかり、タブを表示し続ける必要がある | FFmpeg で実時間より速く書き出す。裏で動かしてもよい |
| 読み込める形式がブラウザ次第（H.265 の MOV などは不可） | FFmpeg で読み、編集用のプロキシ（軽い MP4）を作る |
| 素材ファイルをブラウザ内に丸ごと複製して保存している | 元のファイルの場所を参照し、プロジェクトはフォルダに保存する |
| 書き出し形式がブラウザ次第（H.264 にならないことがある） | 書き出し形式を FFmpeg で固定する（MP4 / H.264 + AAC） |

## 2. 全体の構成

```
┌──────────────── Tauri アプリ ────────────────┐
│  画面（WebView）                              │
│   TypeScript + Vite                           │
│   ・今の HTML/CSS（Spectrum 風）をそのまま使う   │
│   ・タイムライン編集・元に戻す（いまの JS を移植）│
│   ・プレビュー：プロキシを <video> で再生し、     │
│     canvas で合成（いまの再生エンジン）          │
│        │ invoke（命令） ▲ event（進み具合）      │
│        ▼               │                        │
│  Rust（src-tauri）                             │
│   ・プロジェクトの保存・開く・自動保存・履歴     │
│   ・素材の解析（長さ・解像度・サムネイル・波形）  │
│   ・プロキシ作成・無音検出                       │
│   ・書き出し（FFmpeg のコマンドを組み立てて実行）│
│   ・台本アプリの link.json の監視と差分          │
│        │                                       │
│        ▼                                       │
│  FFmpeg / FFprobe（アプリに同梱：sidecar）      │
└───────────────────────────────────────────────┘
```

### 役割の分け方（決めること 1）

**画面側（TypeScript）が持つもの**
- 編集中のプロジェクトの状態
- タイムライン操作（並べ替え・分割・長さ調整・テロップ）
- 元に戻す／やり直し

**Rust が持つもの**
- ファイルの読み書き
- 素材の処理（解析・プロキシ・波形・無音検出）
- 書き出し

こう分ける理由：
- いま動いているタイムラインの処理を、書き直さずに使える。
- 操作のたびに Rust とやり取りしないので、反応が速い。
- 共同作業（beta 以降）を入れる段階で、状態の正本を Rust かサーバーへ移すかを改めて決める。

データの形は Rust の型（serde）を正本とし、`specta`（tauri-specta）で TypeScript の型を自動で作る。画面と Rust で形がずれないようにするため。

### プレビューの方式（決めること 2）

- **第1段階**: 読み込み時に、どの OS の WebView でも再生できるプロキシ（720p / H.264 + AAC の MP4）を作る。プレビューはそれを `<video>` で再生し、canvas で合成する。いまのブラウザ版の方式と同じ。画面のヘッダーにある「プロキシ編集中」の表示とも合う。
- **第2段階（必要になったら）**: 重ねる映像が増えて重くなったら、Rust 側でフレームを作る方式（FFmpeg のライブラリ + wgpu）に切り替える。その場合は、映像を WebView に送る方法を別に検討する。

ローカルのファイルは Tauri の asset プロトコル（`convertFileSrc`）で `<video>` に渡す。読める範囲（scope）は、プロジェクトのフォルダとキャッシュのフォルダに限る。

## 3. 機能ごとの作り方（ブラウザ版との対応）

| 機能 | ブラウザ版（いま） | Tauri 版 |
|---|---|---|
| 読み込み | ファイル選択・ドラッグ、`<video>` で長さとサムネイル、Web Audio で波形 | ダイアログ／ドラッグで場所を受け取る → Rust が `ffprobe` で解析。サムネイル・波形（`ffmpeg` で PCM を取り出してピークを計算）・プロキシを作業キューで作る。進み具合は event で画面へ |
| 素材の保存 | IndexedDB にファイルを複製 | 元の場所を参照（絶対パス＋プロジェクトからの相対パス）。見つからない素材は「リンクし直す」画面で選び直す |
| プロジェクト保存 | IndexedDB に JSON を自動保存 | プロジェクトフォルダに `project.json`（自動保存）＋`cache/`（プロキシ・サムネイル・波形）。変更履歴は SQLite（rusqlite）にスナップショットで残し、「履歴・復元」画面から戻せるようにする |
| カット編集・タイムライン | TypeScript に移植（ロジックはそのまま） | 同左 |
| テロップ | canvas に描いて書き出しにも焼き込む | プレビューは同じ。書き出しでは画面側が書き出し解像度でテロップごとに透明 PNG を作って Rust に渡し、FFmpeg の `overlay`（表示時間を指定）で重ねる。フォントの違いで見た目がずれないようにするため |
| 無音検出 | 波形のピークから判定 | 同じ判定を Rust で行う（細かいピークを使う）。`silencedetect` フィルターとの比較も試し、精度のよい方を採用する |
| 範囲書き出し | 実時間で録画し、イン〜アウトだけ記録 | タイムライン（範囲で切り取ったもの）から FFmpeg のフィルター（`trim`/`atrim`・`concat`・`overlay`・`amix`）を組み立てて一度に書き出す |
| 書き出し形式 | ブラウザが録画できる形式 | MP4（H.264 + AAC）を基本にする。使えるときは OS の機能で書き出す（Windows：`h264_mf` / NVENC など、macOS：`h264_videotoolbox`）。使えないときは `libopenh264` に切り替える。進み具合は `-progress pipe:1` を読んで event で送る。一時停止は使わず、中止と再実行にする |
| 書き出し前のチェック | 尺・権利・見本素材・形式 | 同じ。加えて、元素材が見つかるか、保存先の空き容量を確認する |
| 台本アプリ連携 | 未実装（紐づけボタンのみ） | `notify` で `○○.link.json` を監視する。差分を一覧にし、追加・並べ替え・移動は自動、変更・削除は確認、台本から消えた行のクリップは「孤立クリップ」として扱う（連携仕様書の取り込みルールどおり） |
| 録音（オーディオページ） | 見本のみ | `cpal` でマイク入力、WAV で保存。動画に合わせた録音はプレビュー再生と同期させる（M6） |

## 4. フォルダ構成（案）

```
Yahibo-Matsuko/
├─ src/                         いまのブラウザ版（参照用に残す）
├─ docs/
├─ crates/
│  └─ matsuko-core/             UI を持たない Rust の中心部分（テストしやすくするため分ける）
│     ├─ model.rs               プロジェクト・素材・クリップ・テロップ・範囲・プリセットの型
│     ├─ timeline.rs            長さ・開始位置・範囲の計算（TS 側と同じ結果になるかテストで確認）
│     ├─ export_graph.rs        タイムライン → FFmpeg の引数（フィルター）を組み立てる
│     ├─ silence.rs             無音の判定
│     └─ link.rs                link.json の読み込みと差分
└─ apps/
   └─ editor/
      ├─ src/                   画面（TypeScript + Vite）
      │  ├─ pages/              media / cut / edit / fx / audio / export / script
      │  ├─ timeline/           編集操作・元に戻す
      │  ├─ preview/            再生エンジン（video + canvas）
      │  └─ ipc.ts              Rust への命令（tauri-specta で作った型付き関数）
      └─ src-tauri/
         ├─ tauri.conf.json
         ├─ capabilities/       使ってよい機能の許可（fs の範囲・sidecar・dialog）
         ├─ binaries/           ffmpeg-<ターゲット>、ffprobe-<ターゲット>
         └─ src/
            ├─ lib.rs
            ├─ commands/        project.rs / media.rs / export.rs / link.rs
            ├─ jobs.rs          作業キュー（プロキシ・波形・書き出し）、中止、進み具合
            └─ store.rs         保存・自動保存・履歴（SQLite）
```

使う主な部品：
- **Tauri 2 のプラグイン**: `dialog`、`fs`、`shell`（sidecar 用）、`window-state`、`single-instance`、`log`、`updater`
- **Rust のクレート**: `serde` / `serde_json`、`specta` / `tauri-specta`、`rusqlite`、`notify`、`tokio`、`thiserror`、`cpal`（録音を作る段階で）

## 5. 段階と、それぞれの完成の目安

| 段階 | 内容 | 完成の目安 |
|---|---|---|
| **M0 土台** | Tauri 2 + Vite + TypeScript の雛形。いまの画面を移植して起動。FFmpeg を OS ごとに同梱。GitHub Actions で Windows / macOS / Linux をビルド | 3つの OS でアプリが起動し、見本プロジェクトが表示される |
| **M1 プロジェクトと素材** | 新規・開く・保存・自動保存。読み込み（ダイアログ・ドラッグ）、ffprobe の解析、サムネイル・波形・プロキシ作成のキュー、権利情報の編集、素材のリンクし直し | 30分の 4K 素材を読み込み、プロキシ作成中も操作が止まらない。アプリを閉じて開き直すと続きから作業できる |
| **M2 カット・編集** | タイムライン操作・カットページ・テロップ・無音検出を TypeScript に移植。プロキシでのプレビュー、元に戻す、変更履歴からの復元 | ブラウザ版でできた操作がすべてできる。8分の番組で、プレビューの再生が途切れない |
| **M3 書き出し** | FFmpeg のフィルター組み立て、プリセット、OS の機能で書き出す処理と代わりの処理、キュー・進み具合・中止、範囲書き出し、テロップ焼き込み、書き出し前のチェック | 8分の番組を MP4（H.264 + AAC）で、実時間より速く書き出せる。結果を ffprobe で確かめるテストが CI で通る |
| **M4 台本連携** | link.json の監視、差分の一覧・確認・反映、台本ページ、台本行とクリップの関連。台本連携の設定（紐づける台本ファイル・反映のしかたなど）は、プロジェクト設定（プロジェクト → プロジェクト設定…）に「台本連携」の分類を足して置く | 台本アプリで行を追加・並べ替えすると、確認したうえで編集ソフトに反映される |
| **M5 配布** | コード署名（Windows / macOS の公証）、インストーラー（Windows は管理者権限なしで入る形式、macOS は dmg）、自動更新、ログの収集、学校向けの導入手順書 | 学校の PC に、管理者権限なしで入れて更新できる |
| **M6 beta 以降** | `.swdx` 対応、共同作業（Cloudflare 上の ID・権限・履歴）、録音、色補正などのエフェクト（FFmpeg の `eq` や LUT）、トラッキング | 別途計画する |

進め方：
- M0 → M1 → M2 → M3 を先に進め、「読み込み → カット → 書き出し」をデスクトップ版で動かすことを最初の区切りにする。
- M4 は、台本アプリ側の書き出し（link.json）の仕様が固まってから始める。
- プロジェクト設定（シーケンスの解像度・フレームレート、プレビューの画質、プロキシの高さ、音声のサンプリング周波数）は M3 のあとに作った。設定はプロジェクトの中（`settings`）に保存する。M4 では、ここに台本連携の設定を足す（`apps/editor/src/ui/projectSettings.ts`）。

進み具合：
- M0：済み（3つの OS のビルドが CI で通る）。
- M1：実装済み。プロジェクトフォルダー（`project.json` と `cache/`）、読み込み、ffprobe の解析、サムネイル・波形・プロキシの作業キュー、リンクし直しを作った。
  - 変更履歴の SQLite は、M2 の「変更履歴からの復元」と一緒に作る。
  - 画面の中のドラッグは、Windows で HTML のドラッグ＆ドロップが使えなくなる問題を避けるため、マウス操作で作り直した。
- M2：実装済み。
  - 画面のコードを TypeScript（`apps/editor/src/ui/`）に移し、ブラウザ版の HTML はそこから作るようにした（`npm run build:web`）。動きが変わっていないことは回帰テスト（`tests/tour.mjs`）で確かめた。
  - プロジェクトの型・タイムラインの編集・無音の検出・変更履歴の計算は、型つきの中心部分（`apps/editor/src/core/`）にまとめ、単体テストをつけた。ランダムな操作のテストで、端に近い位置に挿入するとクリップが重なる不具合を見つけて直した。
  - 変更履歴：2分ごとに写しを残し（新しい順に100件）、メニューの「プロジェクト → 変更履歴・復元…」から戻せる。デスクトップ版は `history.sqlite`、ブラウザ版は IndexedDB。
  - プレビュー：8分の番組（96カット・テロップ・BGM・調整レイヤー）で途切れを測った（`tests/playback.mjs`）。素材を読み込むたびの描き直しをやめ、再生の開始を最初の映像の準備ができるまで待つようにした。
  - 画面のモジュールの多くは、まだ型を付けていない（先頭に `// @ts-nocheck`）。M3 以降で、触るところから型を付けていく。
- M3：実装済み。
  - 書き出しの方式：タイムラインを、クリップやテロップが切り替わるところで区間に分け、区間ごとに FFmpeg で映像を作る（使う素材の必要な部分だけを読む）。音声はまとめて作り、最後に区間をつなげて（再エンコードしない）音声と合わせる。組み立ては `crates/matsuko-core/src/export.rs`、実行は `run.rs`。
  - テロップは、画面がプレビューと同じ描き方で PNG にして渡す（クレジットは下から上へ流す）。位置・拡大率・回転・不透明度・調整レイヤー・音量・ミュート・ソロも反映する。
  - H.264 のエンコーダーは、macOS は VideoToolbox、Windows は Media Foundation、どちらも使えなければ OpenH264 の順に試す（最初の区間で失敗したら次へ）。
  - 範囲の書き出し・音声だけ（M4A）・中止・進み具合に対応。デスクトップ版は保存先を先に選び、一時停止はなし（中止してやり直す）。
  - 結合テスト（`crates/matsuko-core/tests/export_ffmpeg.rs`）で、実際に書き出して ffprobe で長さ・形式・解像度・フレーム数を確かめる。CI では配布するものと同じ LGPL 版の FFmpeg を使う。
  - 8分の番組（96カット・テロップ・BGM・調整レイヤー、1080p）の書き出しは、4コアの開発環境・ソフトウェアのエンコードで 324 秒（実時間の 1.48 倍の速さ）。

## 6. テストの方針

- **Rust（`matsuko-core`）**
  - タイムラインの計算、FFmpeg の引数の組み立て、無音の判定、link.json の差分を単体テストする。
  - FFmpeg の引数は「この入力ならこの引数」という見本ファイルと比べる（スナップショットテスト）。
- **素材を使った結合テスト**
  - テスト用の素材は、FFmpeg の `lavfi`（`testsrc`・`sine`・音のある区間とない区間を交互にした音）で作る。ファイルをリポジトリに入れないため。
  - 読み込み → 書き出しまで通し、ffprobe で長さ・形式・解像度を確かめる。
- **画面**
  - Rust との命令を偽物に差し替えて、Playwright で操作テストをする（ブラウザ版の確認でやった方法の延長）。
  - アプリ全体は `tauri-driver`（WebDriver）で、Windows と Linux の CI で動かす。
- **CI**: GitHub Actions で 3 OS をビルドしてテストする。

## 7. 気をつけること・先に決めること

1. **FFmpeg のライセンス**
   - H.264 の書き出しに `libx264` を使うと GPL になり、配布の条件が変わる。
   - そのため、LGPL の FFmpeg に、OS の機能（Media Foundation / VideoToolbox）と OpenH264 を組み合わせる案を基本にする。
   - 配布前に、同梱する FFmpeg のビルド内容とライセンス表記を確認する。H.264 / AAC の特許の扱いも、配布の形に合わせて確認が必要。
2. **WebView の違い**
   - Windows は WebView2（Chromium 系）、macOS は WKWebView（Safari 系）、Linux は WebKitGTK（GStreamer で再生）。
   - プロキシを H.264 / AAC の MP4 にそろえれば、どれでも再生できる見込み。Linux は GStreamer のプラグインの有無に左右されるので、M0 で確認する。
   - M1 で確認：Linux の WebKitGTK は、`asset:` の動画・音声を再生できない（fetch では読める）。Linux だけ、アプリの中の小さなサーバー（127.0.0.1、起動ごとの合言葉つき）から渡す。H.264 の再生には `gstreamer1.0-libav` が要るので、deb の依存に入れた。AppImage は、GPL でビルドされたライブラリを同梱しないよう、GStreamer を同梱しない（PC に入っているものを使う）。
3. **対象の OS の優先順位**
   - 学校の PC は Windows が多いと考え、Windows を最優先、次に macOS とする案。
   - Chromebook では Tauri が動かないため、ブラウザ版も残すかを決める必要がある（決めること 3）。
4. **画面の作り方**
   - まず、いまの「文字列で画面を組み立てる」方式を TypeScript のモジュールに分けて移植する。
   - 画面が増えて保守が難しくなったら、Svelte などの部品化の仕組みに移る。移るかどうかは M2 の終わりに判断する。
5. **アプリの大きさ**
   - FFmpeg を同梱すると、インストーラーが数十 MB 大きくなる。
   - 必要な機能だけを入れた FFmpeg を作って小さくするかは、M5 で判断する。
6. **ブラウザ版のデータの移行**
   - ブラウザ版はファイルをブラウザ内に持っている。
   - 必要なら、ブラウザ版に「プロジェクトを書き出す」（`project.json` と素材を zip にする）を足し、デスクトップ版で取り込めるようにする。
